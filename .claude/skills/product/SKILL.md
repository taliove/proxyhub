# 产品领域(product):需求收敛 + 文档写作

## Part 1 — 需求拷问(原 req-grill)

把一个模糊想法收敛成一份具体需求 spec。**收敛到 spec 即止**:不做实施计划、不拆任务、不写代码(那是后续 Plan 流程的事)。

访谈纪律:一次只问一个问题,每问附上你的推荐答案;能自己查到的事实(代码、文档)不许问用户。

### 0. 开场必读

- `CONTEXT.md` —— 术语表,访谈中所有术语以此为基准
- `AGENTS.md` §3 —— 文档政策,产出物落点不准违反

### 1. 调研 subagent(只读,三个时机)

访谈在主上下文进行;需要摸代码/文档时 dispatch 只读探索型 agent,回报控制在半页简报(模块清单 + 现状行为 + 接缝点),代码细节留在它的上下文。

| 时机 | 何时派 | 任务 |
|---|---|---|
| A 开场背景 | 模糊想法进来,进入阶段 2 前 | 摸相关 internal 包/前端页面/HTTP 接口、现有行为、相关 design-* 与 ADR |
| B 定点核验 | 用户断言了某个现有行为 | 去代码里验证,不一致当场摆出 |
| C 影响清单 | 需求收敛成形、写 spec 前 | 列出受影响模块/接口,可并行派多个(后端/前端/文档) |

**深度纪律:模块/接口级封顶。** 回答"哪个包、哪个接口、哪张表、哪份文档相关",不下钻函数级实现(需求没定稿前函数级清单必过期,且会把访谈拖进实现细节)。

**时序纪律:A 类调研未返回前,不对用户做任何"现状如何"的断言**——意图锁定只复述用户需求,不评论现状。若先给了回复、调研返回后发现事实错误,必须当场显式纠正(明说"我之前说错了"),不带过。

### 2. 四段漏斗

1. **意图锁定**:用一句话复述想法让用户确认("你想解决的是 X,对吗?")。一段话藏多个需求时全部列出,用户只选一个聚焦,其余记入 spec 稿"拆分暂存"区。
2. **现状对齐**:派 A 类调研,摆出"现状 vs 想要"的 gap,确认 gap 真实存在。
3. **拷问循环**:一次一问,先 WHY 后 WHAT——谁、什么场景、什么痛、现在怎么绕、最小可接受的改变是什么。术语歧义当场挑战(对 `CONTEXT.md`),事实断言当场核验(B)。
4. **收敛成稿**:派 C 类调研,写三层产出(§4)。

### 3. 出口标准(全部满足才算收敛)

- [ ] 需求一句话说清,且有至少一个具体用户场景支撑
- [ ] 关键术语全部对上 `CONTEXT.md`(新术语已写入)
- [ ] "不做什么"和"做什么"一样明确
- [ ] 影响模块清单(C)已生成
- [ ] 遗留待决问题已显式列出(允许带着待决结束,不允许藏着)

### 4. 三层产出

1. **主产出 `.scratch/spec/spec-<主题>.md`**(过程稿,永不签入),必含以下小节:

```markdown
# spec-<主题>
## 需求陈述        # 一句话 + 用户场景
## 现状与 gap      # A 类调研结论
## 做什么 / 不做什么
## 影响模块        # C 类调研结论,模块/接口级
## 拆分暂存        # 意图锁定阶段拆出的其他需求
## 遗留待决
```

2. **`CONTEXT.md` 即时更新**:访谈中每敲定一个术语当场写入,不批量积压。CONTEXT.md 只放术语定义,不放实现细节。
3. **ADR 仅提议**:同时满足"难逆转、缺上下文会费解、真实权衡过"才提议写 `docs/adr/`,需求阶段大多数决定够不上,默认不提。

**禁止**:直接写 `docs/` 下任何文件(design 蒸馏是功能落地时的事);把 spec 写进仓库可签入区域。

### 5. 常见错误

| 错误 | 纠正 |
|---|---|
| 一次抛多个问题 | 一次一问,等回答再继续 |
| 把"问用户"当调研 | 事实自己查代码/文档,只把"决策"留给用户 |
| 影响清单写到函数级 | 模块/接口级封顶 |
| 带着模糊术语继续聊 | 当场挑战,敲定即写 CONTEXT.md |
| 收敛后顺手开聊实现方案 | 打住,spec 即止,提示用户走 Plan 流程 |

## Part 2 — 文档写作(原 doc-writing)

任何"写文档"动作之前,先过决策树确定文档种类,再按对应规则执行。文档政策的权威事实源是 AGENTS.md §3;本部分是它的执行流程。文风与语言规范不在此处(AGENTS.md 领地)。

### 1. 决策树:这件事该写哪种文档?

按顺序问,第一个命中的就是答案:

1. **这是一次"为什么这么做"的决策吗?** -> ADR(`docs/adr/NNNN-kebab-case.md`)。ADR 不可变;推翻旧决策 = 写新 ADR 标注 supersede。
2. **它描述"系统是什么/怎么运作",会随代码演进吗?** -> 设计文档(`docs/design-*.md`)。
3. **它教部署/使用者"怎么操作"吗?** -> 用户向文档(`docs/` 大写文件名:DEPLOY.md / SECURITY.md / FAQ.md,或新增同类大写文件)。
4. **它是用户上手必需的最小信息吗?** -> README.md(受 AGENTS.md §3 白名单约束)。
5. **以上都不是(计划/总结/验证/功能工作稿)?** -> **不写进 docs/**。落 `.scratch/`(spec 落 `.scratch/spec/`),永不签入。

### 2. 放置与命名规则

| 种类 | 位置与命名 |
|---|---|
| ADR | `docs/adr/NNNN-kebab-case.md`,编号取现有最大 +1 |
| 设计文档 | `docs/design-<主题>.md`(蛇形) |
| 用户向 | `docs/<大写名>.md`(DEPLOY/SECURITY/FAQ 同族) |
| 开发者入口 | `docs/DEVELOPMENT.md`(唯一) |
| spec(过程产物) | `.scratch/spec/<feature>.md`,禁止出现在 `docs/` |

写文件前先回答"它属于哪一类",答不出 = 不该写。

### 3. 模板

#### ADR 模板

```markdown
# ADR-NNNN: <决策标题>

状态: accepted
日期: YYYY-MM-DD

## 上下文
<迫使做决策的事实与约束>

## 决策
<我们决定做什么>

## 后果
<正面/负面影响,被放弃的备选及原因>
```

#### 设计文档模板

```markdown
# <主题> - 设计

## 概述
<解决什么问题,一段话>

## 模型
<核心数据结构/领域对象>

## 关键流程
<状态机/调用链/时序>

## 与其他模块的边界
<依赖方向,不重复其他 design 文档已覆盖的内容>
```

#### 用户向文档模板

```markdown
# <主题>

<一句话:这份文档帮用户完成什么>

## 前置条件
## 操作步骤
<每步配命令>
## 验证
<怎么确认做对了:命令 + 期望输出>
## 出问题了
<链 FAQ.md 对应条目>
```

### 4. spec 蒸馏规则(功能落地时执行)

spec 是过程稿,落地即退役。删除/过期前,逐节审判:

- **决策(为什么)** -> 进 ADR。没有对应 ADR 就新建。
- **模型/状态机/字段级规则(是什么)** -> 并进对应 `design-*.md`。
- **操作步骤、截图、任务清单、会议记录** -> 丢弃,不迁移。
- 审判完一篇删一篇;`docs/` 下不允许存在 `spec-*.md`。

### 5. README 守卫

README 段落白名单以 AGENTS.md §3 为唯一事实源(不在此复述,防漂移)。修改 README 时逐段对照该白名单:
- 新增段落必须回答"为什么是用户上手必需",答不出就不加。
- 细节一律链出到 docs/,README 只做入口,不做副本(单一事实源)。
- 开发者内容(技术栈/项目结构/make 命令)出现即移去 docs/DEVELOPMENT.md。

### 6. 收尾检查

- [ ] 文档语言为中文
- [ ] 内部链接全部有效(相对路径,目标文件存在)
- [ ] 无凭证/真实节点信息(安全红线,AGENTS.md §7)
- [ ] 新增文档已归入 §2 表格的某一类
