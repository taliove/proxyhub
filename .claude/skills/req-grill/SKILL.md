# 需求拷问(req-grill)

把一个模糊想法收敛成一份具体需求 spec。**收敛到 spec 即止**:不做实施计划、不拆任务、不写代码(那是后续 plan 流程的事)。

访谈纪律继承自通用 grilling:一次只问一个问题,每问附上你的推荐答案;能自己查到的事实(代码、文档)不许问用户。

## 0. 开场必读

- `CONTEXT.md` —— 术语表,访谈中所有术语以此为基准
- `CLAUDE.md` §3 —— 文档政策,产出物落点不准违反

## 1. 调研 subagent(只读,三个时机)

访谈在主上下文进行;需要摸代码/文档时 dispatch 只读探索型 agent,回报控制在半页简报(模块清单 + 现状行为 + 接缝点),代码细节留在它的上下文。

| 时机 | 何时派 | 任务 |
|---|---|---|
| A 开场背景 | 模糊想法进来,进入阶段 2 前 | 摸相关 internal 包/前端页面/HTTP 接口、现有行为、相关 design-* 与 ADR |
| B 定点核验 | 用户断言了某个现有行为 | 去代码里验证,不一致当场摆出 |
| C 影响清单 | 需求收敛成形、写 spec 前 | 列出受影响模块/接口,可并行派多个(后端/前端/文档) |

**深度纪律:模块/接口级封顶。** 回答"哪个包、哪个接口、哪张表、哪份文档相关",不下钻函数级实现(需求没定稿前函数级清单必过期,且会把访谈拖进实现细节)。

**时序纪律:A 类调研未返回前,不对用户做任何"现状如何"的断言**——意图锁定只复述用户需求,不评论现状。若先给了回复、调研返回后发现事实错误,必须当场显式纠正(明说"我之前说错了"),不带过。

## 2. 四段漏斗

1. **意图锁定**:用一句话复述想法让用户确认("你想解决的是 X,对吗?")。一段话藏多个需求时全部列出,用户只选一个聚焦,其余记入 spec 稿"拆分暂存"区。
2. **现状对齐**:派 A 类调研,摆出"现状 vs 想要"的 gap,确认 gap 真实存在。
3. **拷问循环**:一次一问,先 WHY 后 WHAT——谁、什么场景、什么痛、现在怎么绕、最小可接受的改变是什么。术语歧义当场挑战(对 `CONTEXT.md`),事实断言当场核验(B)。
4. **收敛成稿**:派 C 类调研,写三层产出(§4)。

## 3. 出口标准(全部满足才算收敛)

- [ ] 需求一句话说清,且有至少一个具体用户场景支撑
- [ ] 关键术语全部对上 `CONTEXT.md`(新术语已写入)
- [ ] "不做什么"和"做什么"一样明确
- [ ] 影响模块清单(C)已生成
- [ ] 遗留待决问题已显式列出(允许带着待决结束,不允许藏着)

## 4. 三层产出

1. **主产出 `.scratch/spec/spec-<主题>.md`**(过程稿,永不签入),必含以下小节:

```markdown
# spec-<主题>
## 需求陈述        # 一句话 + 用户场景
## 现状与 gap      # A 类调研结论
## 做什么 / 不做什么
## 影响模块        # C 类调研结论,模块/接口级
## 拆分暂存        # 意图锁定阶段拆出的其他需求
## 遗留待决
```

2. **`CONTEXT.md` 即时更新**:访谈中每敲定一个术语当场写入,不批量积压。CONTEXT.md 只放术语定义,不放实现细节。
3. **ADR 仅提议**:同时满足"难逆转、缺上下文会费解、真实权衡过"才提议写 `docs/adr/`,需求阶段大多数决定够不上,默认不提。

**禁止**:直接写 `docs/` 下任何文件(design 蒸馏是功能落地时的事);把 spec 写进仓库可签入区域。

## 5. 常见错误

| 错误 | 纠正 |
|---|---|
| 一次抛多个问题 | 一次一问,等回答再继续 |
| 把"问用户"当调研 | 事实自己查代码/文档,只把"决策"留给用户 |
| 影响清单写到函数级 | 模块/接口级封顶 |
| 带着模糊术语继续聊 | 当场挑战,敲定即写 CONTEXT.md |
| 收敛后顺手开聊实现方案 | 打住,spec 即止,提示用户走 plan 流程 |
