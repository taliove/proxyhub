# 文档写作流程(doc-writing)

任何"写文档"动作之前,先过决策树确定文档种类,再按对应规则执行。文档政策的权威事实源是 CLAUDE.md §3;本 skill 是它的执行流程。文风与语言规范不在此处(CLAUDE.md 领地)。

## 1. 决策树:这件事该写哪种文档?

按顺序问,第一个命中的就是答案:

1. **这是一次"为什么这么做"的决策吗?** -> ADR(`docs/adr/NNNN-kebab-case.md`)。ADR 不可变;推翻旧决策 = 写新 ADR 标注 supersede。
2. **它描述"系统是什么/怎么运作",会随代码演进吗?** -> 设计文档(`docs/design-*.md`)。
3. **它教部署/使用者"怎么操作"吗?** -> 用户向文档(`docs/` 大写文件名:DEPLOY.md / SECURITY.md / FAQ.md,或新增同类大写文件)。
4. **它是用户上手必需的最小信息吗?** -> README.md(受 CLAUDE.md §3 白名单约束)。
5. **以上都不是(计划/总结/验证/功能工作稿)?** -> **不写进 docs/**。落 `.scratch/`(spec 落 `.scratch/spec/`),永不签入。

## 2. 放置与命名规则

| 种类 | 位置与命名 |
|---|---|
| ADR | `docs/adr/NNNN-kebab-case.md`,编号取现有最大 +1 |
| 设计文档 | `docs/design-<主题>.md`(蛇形) |
| 用户向 | `docs/<大写名>.md`(DEPLOY/SECURITY/FAQ 同族) |
| 开发者入口 | `docs/DEVELOPMENT.md`(唯一) |
| spec(过程产物) | `.scratch/spec/<feature>.md`,禁止出现在 `docs/` |

写文件前先回答"它属于哪一类",答不出 = 不该写。

## 3. 模板

### ADR 模板

```markdown
# ADR-NNNN: <决策标题>

状态: accepted
日期: YYYY-MM-DD

## 上下文
<迫使做决策的事实与约束>

## 决策
<我们决定做什么>

## 后果
<正面/负面影响,被放弃的备选及原因>
```

### 设计文档模板

```markdown
# <主题> - 设计

## 概述
<解决什么问题,一段话>

## 模型
<核心数据结构/领域对象>

## 关键流程
<状态机/调用链/时序>

## 与其他模块的边界
<依赖方向,不重复其他 design 文档已覆盖的内容>
```

### 用户向文档模板

```markdown
# <主题>

<一句话:这份文档帮用户完成什么>

## 前置条件
## 操作步骤
<每步配命令>
## 验证
<怎么确认做对了:命令 + 期望输出>
## 出问题了
<链 FAQ.md 对应条目>
```

## 4. spec 蒸馏规则(功能落地时执行)

spec 是过程稿,落地即退役。删除/过期前,逐节审判:

- **决策(为什么)** -> 进 ADR。没有对应 ADR 就新建。
- **模型/状态机/字段级规则(是什么)** -> 并进对应 `design-*.md`。
- **操作步骤、截图、任务清单、会议记录** -> 丢弃,不迁移。
- 审判完一篇删一篇;`docs/` 下不允许存在 `spec-*.md`。

## 5. README 守卫

README 段落白名单以 CLAUDE.md §3 为唯一事实源(不在此复述,防漂移)。修改 README 时逐段对照该白名单:
- 新增段落必须回答"为什么是用户上手必需",答不出就不加。
- 细节一律链出到 docs/,README 只做入口,不做副本(单一事实源)。
- 开发者内容(技术栈/项目结构/make 命令)出现即移去 docs/DEVELOPMENT.md。

## 6. 收尾检查

- [ ] 文档语言为中文
- [ ] 内部链接全部有效(相对路径,目标文件存在)
- [ ] 无凭证/真实节点信息(安全红线,CLAUDE.md §7)
- [ ] 新增文档已归入 §2 表格的某一类
