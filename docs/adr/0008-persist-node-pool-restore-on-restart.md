# ADR 0008: 节点池持久化,重启后回填

## 状态

已接受

## 上下文

聚合器的节点池是纯内存态(`Aggregator.nodes`),进程退出即丢。启动时只有"跑一轮聚合"能重建它。而定时刷新可关闭(ADR 0004),关闭后启动那一轮也被跳过——于是每次重启节点池必为空,直到手动刷新一次。

库里的 `node_health` 表只存健康检查的统计快照(name/available/latency),不含 server/port/uuid/password 等连接参数,无法据此重建节点。

## 决策

新建 `nodes` 表,存放最近一次成功聚合的**完整节点池**(含全部连接参数 + region/source/健康状态 + position 顺序)。

- **写:** 每轮成功聚合、内存池更新后,全量替换该表(事务:先 DELETE 再批量 INSERT),与内存池保持一致。写库失败只告警、不阻断本轮。
- **读:** `aggregator.New()` 里从库回填内存池,使进程重启后立即有节点可用,与刷新开关完全解耦。

## 理由

- 用户要的是"不自动周期刷新",不是"重启后清空"。持久化让这两件事解耦。
- 全量替换而非增量:内存池本就是每轮整体替换,库与内存同构最简单、无脏数据。
- 结构化表(而非 settings 里塞 JSON):节点状态页本就要按行展示,结构化利于未来查询/单节点操作。

## 后果

- 节点连接参数(含机场节点密码/uuid)落库。本就是单机 SQLite 单文件部署(ADR 0003),风险等同订阅本身;不额外加密。
- `nodes` 表与 `self_hosted_nodes` 表职责不同:后者是用户配置的常驻自建节点(输入),前者是聚合产出的快照(输出,含自建节点注入后的最终池)。
- 全量拉取失败时保留旧内存池(既有行为),但**不覆盖**库快照——库里仍是上一次成功的池,重启回填到的就是它。
