# ADR 0040: 订阅可用性三态语义(从未检测放行)

## 状态

accepted

## 日期

2026-08-03

## 上下文

生产事故(issue #32):用户新建 url 型机场(URL 被 Cloudflare 拦截拉不通),手动粘贴导入 341 个节点。节点管理页显示几百个节点,但订阅地址与「节点范围」预览恒为空(命中 0 / 共 0),去掉全部筛选条件依然为 0,且无任何原因提示。手动机场场景同构:粘贴导入的节点在手动检测之前订阅恒空——用户粘贴节点就是为了用,拿到的却是空订阅。

根因是语义混淆:`internal/filter` 的 `FilterAvailable` 无条件丢弃 `Available=false` 的机场节点,而节点零值即 `Available=false`——手动导入(明确不跑健康检查)与拉取入池的节点在被任何检测触碰前都是这个状态。于是「从未检测(未知)」与「已确认死亡」共用一个布尔值,在订阅路径上同价丢弃,大量可能活着的节点被静默判死刑。

「从未检测」的可靠判据已存在:`subscription.Node.DetectionKind == ""`(空 = 从未检测;`DetectionLastCheck` 不能担此任,见「后果」中被放弃的备选)。订阅过滤链(server 层 `filteredNodes`)是 `FilterAvailable` 的唯一调用方,爆炸半径可控。

另一个必须配套解决的问题:未检测节点 `Latency=0`,若直接放行,会在 `sortByLatency` 升序中顶到最前、在 `selectBestByRegion` 每地区前 N 中挤掉真实好节点、在 `deduplicateNodes` 中赢过同 key 的已验证节点——放行必须配套排位修正。

## 决策

1. **订阅过滤链三态化**。`FilterAvailable` 按三态处理机场节点:`DetectionKind == ""`(从未检测)放行;已检测且 `Available == true` 放行;已检测且 `Available == false`(已确认死亡)过滤。核心语义:**从未检测 ≠ 已确认死亡**。自建节点豁免逻辑不变。
2. **未检测节点在延迟比较中视为 +∞**。`sortByLatency` / `selectBestByRegion` / `deduplicateNodes` 三处做延迟比较时,未检测节点的比较延迟视为 +∞——只改比较,不改节点数据(`Latency=0` 原样保留,不影响后续检测写回)。效果:已知好节点优先;去重时验证过的节点胜出;每地区精选中未检测节点不挤占已检测节点名额,仅在地区内已检测不足 N 时补位。
3. **延迟阈值过滤对未检测节点放行**。同一过滤链上的第四处延迟语义 `FilterByLatencyThreshold` 不做 +∞ 处理:未检测节点 `Latency=0` 恒不超过阈值,天然通过。这是有意为之而非遗漏——阈值被配置加载强制为正,若对未检测节点按 +∞ 处理,它们会被阈值全部滤掉,原地重现本 ADR 要解决的事故。未检测节点的延迟未知性由其「未验证」身份承担(排位垫后),不进阈值门禁;后续者对链上延迟语义做「对齐」时不得动这一处。
4. **判据只用 `DetectionKind == ""`**,不引入新字段、新配置。

本文是对 ADR 0002(健康检查两阶段检测语义)、ADR 0005(订阅时过滤)、ADR 0009(节点管理筛选口径)的补充细化:在其语境下把订阅可用性过滤从两态细化为三态,不推翻其中任何条款。

## 后果

正面:

- 手动导入即可用:粘贴导入的节点在首次检测前即可随订阅下发,消除「导入即空订阅」的静默失败。
- 变更单向安全:正常订阅内全是已检测节点,相对排位不变;空订阅从空变有;「只发验证过的节点」的严格语义跑一轮检测自动恢复(已确认死亡的节点依然被过滤)。
- 未检测节点进下发集后,订阅测试的 full probe 会顺带实测它们——检测覆盖率提升(单次任务体量变大,属正收益)。

外部可见的口径变化(两处,必须明示):

1. **`/sub/{path}` 下发内容集变大**:含从未检测的节点。对正常订阅,已检测节点的相对排位不变(未检测节点排后);对原先会产出空的订阅,从空变有。客户端会收到比以往更多的节点,其中一部分尚未验证——这是本决策的目标行为。
2. **订阅列表「可用 x/y」与订阅测试快照口径**:`y` = 会下发的节点数(含未检测),`x` = 已确认可用的节点数。两者不再同义,「可用」一词在 UI 上的含义收窄为「已确认可用」。

旧数据边角:早期快照可能存 `Available=true` + `DetectionKind==""` + 真实 Latency 的节点,新语义下被当未检测排 +∞(原按真实延迟排)。一轮全量刷新的 checkHealth 即翻态为 health,自愈,不阻断。

被放弃的备选:

- **以 `DetectionLastCheck` 非空判「已检测」**:TCP 快检判死只写 `DetectionKind=health`、不写 `DetectionLastCheck`,以时间戳作判据会把已被快检确认死亡的节点当作从未检测而误放——方向性错误,否决。
- **加时间衰减(未检测超时后重新过滤)**:「未知」态的收敛已有归属——URL 机场靠全量刷新的 checkHealth 一个周期内翻态;URL 全灭场景归 issue #34(中止分支保留池快检);手动机场按设计不收敛(未检测即放行,正是本决策的目标行为)。另加衰减是重复机制,否决。
- **加逃生开关(可配置恢复两态)**:变更单向安全(见上),无真实风险场景需要回退开关;真要回退,revert 单 commit 即可,无 schema/数据变更,回退干净。否决。

关联 issue:#33(检测持久化)、#34(保留池快检)、#35(UI 可观测性:「未检测」标记与 `detection_kind` 字段暴露),各自独立实施,本决策不阻塞它们。
