# ADR 0002: 健康检查采用延迟测速 + 真实请求测试

## 状态

已接受

## 上下文

订阅聚合系统需要验证节点可用性，过滤掉不可用节点。从多个机场拉取的节点中，可能存在：
- 网络不通的节点
- 延迟极高的节点
- 能连接但无法翻墙的节点

需要选择合适的健康检查策略。

## 决策

采用**两阶段健康检查**：

### 阶段 1：延迟测速
- 测量到节点的网络延迟
- 阈值：< 500ms
- 目的：快速过滤掉网络不通或延迟过高的节点

### 阶段 2：真实请求测试
- 通过节点访问目标网站（google.com）
- 验证 HTTP/HTTPS 请求能否成功完成
- 目的：确保节点真的能翻墙

只有通过两个阶段的节点才标记为"可用"，加入聚合订阅。

检查频率：每 10-15 分钟全量检查一次。

## 备选方案

### 方案 A：仅 TCP 连通性检查
- 优点：最快，资源消耗最少
- 缺点：无法验证节点真的能用，可能出现"能连但不能翻墙"的节点

### 方案 B：仅延迟测速
- 优点：快速，能过滤高延迟节点
- 缺点：无法验证翻墙能力，可能误判

### 方案 C：仅真实请求测试
- 优点：最准确
- 缺点：慢，需要对每个节点建立完整代理连接并发起 HTTP 请求

## 理由

### 准确性与效率平衡
- 延迟测速快速过滤掉明显不可用的节点（网络不通、延迟超高）
- 真实请求测试只对低延迟节点执行，避免浪费时间
- 两阶段结合，既保证准确性又控制检查时间

### 用户体验保障
- 终端设备订阅到的节点都是"经过验证可用"的
- 避免用户刷新订阅后，拿到一堆连不上或不能翻墙的节点

### 及时性
- 10-15 分钟的检查频率，能在一刻钟内发现节点状态变化
- 对于 15 台设备的规模，这个延迟可以接受
- 不会太频繁，避免被机场检测为异常请求

### 成本可控
- 假设 3 个机场，每个 50 个节点，共 150 个节点
- 并发检查，单次检查约 5-8 分钟
- 每小时 4-6 次检查，流量消耗约 100-200MB（延迟测速 + 小文件 HTTP 请求）
- 成本可忽略不计

## 后果

### 正面
- 聚合订阅中的节点质量有保障
- 用户无需手动测试节点
- 节点问题能及时发现并告警

### 负面
- 相比简单的 TCP 检查，资源消耗更高
- 可能存在误判（节点在检查时可用，但用户使用时不可用）
- 检查请求可能被机场检测（但 10-15 分钟频率风险较低）

### 中性
- 需要选择合适的测试目标（google.com 稳定但在某些地区被深度封锁）
- 可能需要配置多个测试目标作为备选

## 实现注意事项

1. **并发控制**：检查 150 个节点时，限制并发数（如 20-50），避免过载
2. **超时设置**：每个检查设置合理超时（延迟测速 5s，真实请求 10s）
3. **重试机制**：单次失败不应立即标记为不可用，可以重试 1-2 次
4. **日志记录**：记录检查结果，便于分析节点稳定性趋势
